# Crimson Phase 4D Aligned Stimulus Decode

Date: 2026-07-12

Phase 4D adds headless stimulus decoding driven by Crimson's logical camera
frame identity. It does not render the stimulus or add an independent stimulus
clock. Composite Metal presentation remains Phase 4E.

## Portable Decode Policy

`src/stimulus_playback_coordinator.*` converts each resolved camera frame into
one of four backend-neutral decoder actions:

- `Clear`: the camera frame is missing or outside the repository extent;
- `Hold`: the exact mapped stimulus frame is already buffered;
- `Follow`: continue bounded sequential decoding toward a forward target; or
- `Seek`: settle exactly after a discontinuity, mapping gap, backward request,
  evicted target, or forward jump beyond the decode window.

The coordinator consumes `StimulusRepository`; it does not know about
TensorStore, AVFoundation, CUDA, OpenGL, or Metal. NVIDIA and macOS therefore
share the same corrected/legacy mapping result and decode-target policy.

The stimulus never receives a frame-rate clock. A caller supplies the current
camera frame, and the coordinator uses the resulting mapped stimulus identity.
Repeated mappings hold one stimulus frame across multiple camera frames.

## Apple Session

`src/platform/macos/apple_stimulus_playback_session.*` owns:

- one `StimulusRepository` implementation;
- one portable `StimulusPlaybackCoordinator`; and
- one `AppleVideoPlaybackBuffer` with stream identity `stimulus`.

The session accepts an already-open repository. Storage ownership therefore
stays outside the decoder, and a future repository implementation does not
change the VideoToolbox path. The session exposes exact aligned frames carrying
both the mapping resolution and the decoded frame metadata.

Normal mapped progress calls `setTargetFrame()` with playback disabled. Exact
discontinuities call `requestSeek()`. No Phase 4D code calls the playback
buffer's autonomous `setPlaybackState(..., true, fps)` mode.

Metrics distinguish mapped, missing, and out-of-range camera requests and count
hold, follow, seek, and failed decoder actions. Existing playback-buffer metrics
remain available for decoded, evicted, discarded, and peak-buffered frames.

## Headless Coverage

`stimulus_playback_coordinator_tests` is a portable C++ test covering:

- first-target and post-gap seeks;
- bounded forward following;
- exact buffered holds;
- repeated mappings after eviction;
- backward requests;
- explicit discontinuities; and
- missing and out-of-range clearing.

`apple_stimulus_playback_tests` uses the public repository contract with a
12-frame deterministic video generated by the existing provider-test writer.
Each source frame has a distinct luma value. The test verifies both mapped frame
metadata and decoded pixel content for corrected-direct, corrected-metadata,
legacy fallback, repeated, missing, boundary, backward-seek, and suspend/resume
cases. It also rejects a mapped identity beyond the source video's frame extent.
The decoder queue remains bounded at four frames and does not advance its target
autonomously while settled.

The separate `stimulus_repository_tests` continues to materialize the mapping
contract as a temporary TensorStore Zarr v3 archive. Together these tests keep
media generation independent from TensorStore while exercising both sides of
the production boundary without a GUI or network share.

## Production Probe

`apple_stimulus_playback_probe` joins the real components: it opens an analysis
Zarr with `ArchiveContext`, opens the resolved source video through the Apple
session, maps selected camera frames, and requires the decoded stimulus frame
number to equal the repository result exactly.

```bash
build/macos-arm64-release/apple_stimulus_playback_probe \
  /path/to/recording_analysis.zarr 1023 1024 1025 69512 139023 139024
```

On the representative GoodCopBadCop archive, the re-encoded stimulus MP4 passed
the production probe across the mapping extent:

| Camera frame | Mapping status | Stimulus frame | Result |
| ---: | --- | ---: | --- |
| 1023 | missing | - | no decode requested |
| 1024 | mapped | 0 | decoded 0 |
| 1025 | mapped | 2 | decoded 2 |
| 69512 | mapped | 82180 | decoded 82180 |
| 139023 | mapped | 165578 | decoded 165578 |
| 139024 | out of range | - | no decode requested |

Measured exact-seek settlement was approximately 32 ms at the midpoint and
46 ms at the final mapped frame while reading the network-mounted recording.
The replacement is H.264 Main profile, 344 by 344, 120 fps, with 165579 frames.
The probe establishes indexed decode reachability and mapping identity. It does
not by itself compare replacement pixels with the overwritten source asset.

The replacement must preserve scientific frame identity:

- retain every source frame in order, with no dropped or duplicated frames;
- retain the intended 120 fps timing and at least all mapped stimulus identities;
- use a seekable keyframe structure supported by AVFoundation;
- preserve dimensions, color metadata, and visually lossless scientific content;
  and
- pass the production probe at the first, adjacent, midpoint, final mapped, and
  out-of-range camera positions.

Do not update Zarr mapping arrays merely to accommodate a lossy or frame-changing
transcode. If the replacement changes frame numbering, it requires a deliberate
new alignment run and parity validation.

## Phase Boundary

Phase 4D establishes the shared mapping-to-decoder contract and proves exact
Apple decode identity with deterministic and production media. The production
re-encode gate is closed. Phase 4E subsequently added atomic camera/stimulus
Metal presentation and measurable skew without introducing another clock. See
[the Phase 4E composite presentation record](crimson_macos_phase4e_composite_stimulus_presentation.md).
