# Compact Crop-Geometry Memory Checkpoint

Date: 2026-07-29

Status: compact resident representation accepted. This checkpoint does not
claim that crop payloads are pageable yet, and it is not a long-run RSS or
storage-profile promotion result.

## Scope

The previous full-duration attribution run identified crop geometry as the
largest application-owned retained structure at 199.9 MiB. Crimson stored one
row object per crop plus a per-frame hash map. This change replaces that
representation with:

- one dense `frame_row_offsets` vector;
- compact column vectors for placement and optional geometry;
- identity elision when ROI row IDs equal their row positions; and
- stable grouping by camera frame, preserving the existing first-row
  presentation behavior for frames containing more than one row.

Current-frame resolution remains synchronous, memory-only, and O(1). The
repository performs no TensorStore or network read on the GUI thread. The
retained offsets and column boundary are the basis for a later byte-budgeted
resident/pageable policy; the payload in this checkpoint remains resident.

Implementation commit:

`9e5dd54c86a86d4222c63cacb570b2a888748bc1`

Both mounted trials reported `crimson_worktree_dirty=false`.

## Result

The same 1,188,000-frame mounted Sleepyfish hybrid fixture and production
64 MiB TensorStore cache were used for the baseline and both compact trials.

| Metric | Row/hash baseline | Compact repetition 0 | Compact repetition 1 |
| --- | ---: | ---: | ---: |
| Crop retained lower bound | 199.9 MiB | 62.6 MiB | 62.6 MiB |
| Required-ready retained lower bound | 598.3 MiB | 461.1 MiB | 461.1 MiB |
| Required-ready process RSS | 1,759.8 MiB | 1,572.7 MiB | 1,585.0 MiB |
| Lifetime peak RSS | 1,806.8 MiB | 2,353.4 MiB | 1,854.9 MiB |
| Loading elapsed | 59.3 s | 64.5 s | 60.5 s |
| Total workload | 99.6 s | 97.7 s | 92.9 s |
| RSS after repository release | 343.6 MiB | 355.3 MiB | 903.4 MiB |

The application-owned crop lower bound fell by **137.3 MiB (68.7%)** and was
identical in both compact trials. The required-ready lower bound fell by the
same amount, as expected. Required-ready process RSS was 174.8--187.1 MiB
lower in the two compact trials.

Lifetime peak and post-release RSS were not stable. Compact repetition 0
peaked later during random mask/shape/eye settlement, while repetition 1 did
not reproduce that peak. Post-release RSS also differed by 548 MiB between
the compact repetitions even though both had destroyed the same repositories.
Those values include filesystem and TensorStore state, allocator retention,
and OS page residency, and cannot be attributed to the compact crop owner.
They remain visible in the raw receipts and comparison plot rather than being
used as a promotion claim.

## Correctness And Portability

Focused tests cover empty frames, gaps, unsorted input, multiple rows in one
frame, stable first-row resolution, optional-field validity, implicit ROI row
IDs, and the compact memory bound. The complete macOS suite passed 63/63. An
isolated Linux build passed the focused repository test and built the full
CUDA/NVIDIA `redgui` target.

The repository and memory contract are backend-neutral. Metal, CUDA, and the
GUI are not involved in the compact indexing decision.

## Decision

Keep the compact representation. Do not add synchronous payload paging to the
current-frame path. The next safe steps are:

1. construct compact columns directly in the strict and compatibility openers
   so startup does not first materialize the legacy row representation;
2. apply the same measured compact-index analysis to subject-shape and
   eye-geometry placement metadata;
3. add a byte-budgeted resident/pageable crop payload policy only when a
   larger multi-instance fixture demonstrates that 62.6 MiB no longer fits the
   intended resident budget; and
4. preserve complete frame row ranges in the storage/repository contract even
   while the existing crop inset continues to choose one row for presentation.
